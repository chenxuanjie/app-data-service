# 字段级冲突处理

当前六类业务仍使用 `/v2/sync/upload` 与 PowerSync 复制，不引入自研复制引擎。
能力接口新增 `record_merge: "three_way_v1"`，供客户端在上传前确认配套支持。

Mutation 新增可选 `base_record`：客户端编辑前的完整业务记录，按 entity_type
严格校验字段、十进制金额、标识与 payload；记录 ID 必须与 record_id 相同。
它是比较输入，不是访问凭据；数据集权限、RLS、锁等待超时保持原有校验。
该输入随客户端持久队列保存，而不在服务端增加全量历史快照表。

1. 首先按原修改 ID 检查回执，包含基线的内容摘要也必须相同。
2. 普通记录候选与当前业务内容相同、或双方均删除：返回 applied 和当前版本，不重复写入。
   两项自动偏好仍需保存实际编辑时间，以免较早的离线编辑随后覆盖新值。
3. 有比较基线时，按基线/候选/当前记录三方比较：不同字段自动合并；相同字段
   的同值修改合并；真正不同值保留冲突。对象递归，明细数组视为一个字段。
4. sortOrder 不单独制造冲突；双方并发不同顺序保留当前顺序。
   两项自动偏好继续按实际 edited_at 判定，不以到达时间覆盖。
5. 非法的合并组合（如残值超过新价格）保留合法双方供选择。
6. 删除与有效内容修改不能静默合并；候选选择也要校验用户看到的当前版本。
7. 冲突候选先保留不冲突的服务端字段；解决时再次合并此后的非相关修改，避免整行回写。

工资 payload.updatedAt 为派生修改时间，不构成独立业务冲突；其他金额、名称、备注
等不受设备时间优先规则控制。数字比较使用 Decimal，原始金额精度不改变。

没有基线的已存队列不会被伪造基线、删除或整体重置；内容不同且无可靠前序时保留冲突。
保留现有回执、账号隔离、事务原子性及重试行为。PowerSync 规则不变，本项不新增 SQL
结构迁移；配套自动偏好仍使用 0009_preference_edit_time。

客户端规则说明：`zheri/docs/sync-conflict-policy.md`。NAS 尚需部署包含本功能的新 API
后才能验收跨端真实业务；本机 PostgreSQL 和自动测试不代替该部署验收。
